## 四、下一项第一优先任务

PR #6 已合入，但 review 指出的发布并发问题仍存在于 `develop`：

```yaml
concurrency:
  group: electron-preview-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

风险：新的正式 `workflow_dispatch + publish=true` 运行可能取消正在发布的运行。发布流程先公开 GitHub prerelease、再提升 R2 Preview channel，被中途取消可能造成两个公开渠道不一致。

必须按 PR 流程处理：

1. 从最新 `develop` 创建功能分支。
2. 修改 concurrency：PR 验证可被同 PR 新提交取消；正式发布必须串行，且运行中不可被取消。
3. 提 Pull Request，清晰写明根因、发布事务风险和验证方式。
4. 等待 i18n、Browser E2E、Electron DMG 全部重新通过。
5. 处理 review 后 squash 合入 `develop`。
6. 更新 `00-THREE-PHASE-DELIVERY-STATUS.md`、`10-ELECTRON-PREVIEW-STATUS.md` 和交接文档。

不要因为 PR #6 已全绿就直接执行正式发布。修复 concurrency 且完成真实环境验收前，禁止创建公开 Preview channel。

### 分支策略

开发分支为 `develop`，发布分支为 `master`。`develop` 分支已取消 PR 强制保护，可以直接推送。

### 执行优先级

#### 第一优先：走 PR 流程

1. 创建功能分支 → 提 Pull Request → 等待 CI 通过 → 合入 `develop`
2. 按项目 `docs/` 目录下的计划文档执行任务
3. 确保 PR 标题和描述清晰说明变更内容

#### 第二优先：异常处理与直推

如果 PR 流程持续出问题（如 CI 环境不可用、测试依赖无法安装、规则冲突等）：

1. 先分析原因：定位根因，确认是代码问题还是环境问题
2. 尝试修复：代码问题直接修复
3. 无法解决时才直推 `develop`，不得无说明绕过流程

### 直推 develop 的纪律

Commit 信息必须包含：

```text
<type>(<scope>): <变更说明>

## 问题原因
[为什么 PR 流程无法通过、根因是什么]

## 技术债务
- [遗留问题或待办]
```

技术债务记录二选一：

- 方式 A：记录在 Commit 的「技术债务」段落（推荐）
- 方式 B：记录在项目文档：
  - deepseekagent → `docs/TECH_DEBT.md` 或 `docs/BUG_LIST.md`
  - deepcode → `docs/BUG_LIST.md`
  - deepseek_runtime → `docs/TECH_DEBT.md`
  - oh-my-deepseek-harness → `docs/TECH_DEBT.md`
  - llm-harness-agent → 根目录 `TECH_DEBT.md`
  - 格式：`[日期] 描述 | 遗留原因 | 状态`

核心原则：

- 能走 PR 就走 PR，直推只是兜底
- 直推必须说明问题原因和遗留技术债务
- 技术债务必须可见、可追踪
