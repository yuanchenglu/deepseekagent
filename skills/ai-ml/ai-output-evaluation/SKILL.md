# AI 模型产出评测

## 概述

对 AI 模型的代码产出物进行系统化评测：对比原始项目、运行验证、截图取证、结构化打分。
适用于方舟众测、模型对比评测、AI 代码质量评审等场景。

## 核心原则

### 以任务为单位，逐个推进
**铁律：一次只处理一个任务。** 把该任务下所有模型的产物全部分析、截图、打分完毕后，
再进入下一个任务。禁止一次性铺开所有任务。

用户原话："我希望你一个任务一个任务来，先把第一个任务分析完，然后该截图截图，该打分打分，搞完之后再搞下一个。"

### Diff 优先
在阅读任何产物代码之前，必须先用 diff 对比原始项目与产物。
禁止直接打开产物文件从头读，把原始项目就有的内容误判为模型产出。

### 截图必须验证
截图后必须反查确认截图内容正确，不能盲信截图工具的返回。
每张截图配说明文字，放在对应任务的打分子目录下。

## 工作流程

### 阶段一：信息收集（每个任务开始前）

1. **读任务清单**：了解任务需求、验收点、备注
2. **读映射关系**：确认任务编号、模型代号、产物前缀的对应
3. **检查产物完整性**：哪些模型有产物，哪些缺失
4. **读官方任务书**（如有）

### 阶段二：逐模型分析

对每个模型的产物，按以下顺序执行：

#### 1. 读 TASK_LOG.md
- 了解模型做了什么、为什么这么做
- 注意：TASK_LOG 可能在产物根目录，也可能在子目录（如 h5web/）
- 如果根目录没有，搜索子目录

#### 2. Diff 对比
```bash
diff -rq "原始项目路径/" "产物路径/" | grep -v '.DS_Store' | grep -v 'node_modules'
```
- 只看 diff 输出的差异文件
- 记录：修改了哪些文件、新增了哪些文件、删除了哪些文件
- 统计改动行数
- **检查两个入口文件都要看**：h5web/index.php（主入口如 edu.7color.vip/）和 studytools/index.php（子路径入口）。
  有些模型只改了其中一个，导致另一个入口无变化。diff 两个文件的行数都要记录，差异大的情况说明模型只完成了部分集成工作。

#### 3. 代码审查
- 检查 PHP/Python/JS 语法：`php -l` / `python -m py_compile`
- 检查关键功能实现是否完整
- 检查配置文件（.env.local、PM2 配置等）

#### 4. 运行验证
- 启动本地服务器（PHP/Node）
- 用浏览器访问并截图
- 验证核心功能是否正常工作

#### 5. 平台轨迹查看
- 登录众测平台，查看该模型的执行轨迹
- 不能只看 TASK_LOG，平台轨迹更详细
- 注意工具调用次数、执行时间、重试次数

### 阶段三：截图

#### 截图要求
- 至少 5 张/任务，且每个模型 3-5 张（建议每模型 4 张作为目标）
- 4个模型的任务总截图目标：~16 张
- 覆盖：主界面、核心功能、加载/错误状态、特殊布局差异
- 命名：`{任务编号}_{模型名}_{中文描述}.png`
- 放在 `4打分/{任务编号}_{任务标题}/` 目录下

#### 截图内容
1. 主界面（默认状态）
2. 核心功能操作（如点击按钮后的状态）
3. 加载/错误状态
4. 移动端视图（如适用）
5. 配置文件内容

#### 截图验证
截图后用 `vision_analyze` 或 `browser_vision` 反查确认内容正确。

### 阶段四：打分

#### 评分维度
- **需求完成度** (0-5)：核心需求是否满足
- **代码质量** (0-3)：结构、安全性、可维护性
- **轨迹质量** (0-2)：过程是否可复现、是否有验证闭环

#### 封顶规则
- 核心需求未完成 → 总分 ≤ 6
- 不可运行/不可验证且无修复指引 → 总分 ≤ 4
- 明显跑题 → 总分 ≤ 2

#### 打分文件结构

纯文本 `.txt`，不是 Markdown。口语化，有具体技术细节。

**每个产物(模型)的段落结构：**
1. 标题行（产物名称）
2. 分数行（标准格式）
3. 验收过程（逐条对照）
4. 代码质量
5. 轨迹质量
6. 执行效率
7. 截图说明

### 标准格式模板（强制遵循）

**分数行硬格式（逐字复制，不可变通）：**
```
总分 X/10：需求 A/5；代码 B/3；轨迹 C/2。封顶：是/否（原因）。
```
错误示例：`【综合表现】8/10` ❌、`需求完成度 4/5 + 代码质量 2/3 + 轨迹质量 1/2 = 总分 8/10` ❌
正确示例：`总分 8/10：需求 4/5；代码 2/3；轨迹 2/2。封顶：否。`

**完整模板：**
========================================
产物一：{模型名}
========================================

总分 X/10：需求 A/5；代码 B/3；轨迹 C/2。封顶：是/否（原因）。

验收过程：
（逐条对照任务验收点，说明过没过、为什么。附文件名、行号、命令输出作为证据）

代码质量：
（结构、安全性、可维护性，有问题就说清楚）

轨迹质量：
（TASK_LOG 是否清晰、是否有 UDDP 文档、硬编码路径等）

执行效率：
（基于 TASK_LOG 推断的交互步数、是否有大量无效重试、是否绕弯路）

截图说明：
{文件名}.png
  拍的是什么。第一反应。好在哪里/不好在哪里。
{文件名2}.png
  ...

========================================
产物二：{模型名}
========================================
...
```

当需要同时满足本地评分和平台三维评分时，可以使用这种格式（与标准格式不冲突）：

```text

（逐条对照验收点，附文件名和行号）

...

...

...

{文件名}.png
  说明文字。

========================================

========================================
...
```

### 关于截图说明的位置

截图说明放在每个产物段落的**最后**，紧跟「执行效率」之后。

### 交付效率评分细则（基于平台统计数据）

平台提供以下统计数据，用于评估每个模型的交付效率：

| 指标 | 说明 |
|------|------|
| 耗时 | 模型完成任务的总时间 |
| 用户轮次 | 用户交互次数（通常为1） |
| 工具轮次 | 模型调用工具的总次数 |
| 工具分布 | TodoWrite/Read/Write/Bash/Edit/Glob/Grep/Agent/WebFetch/Execute_code/Process等各类工具调用次数 |

**高效标准（8-10分）：**
- 耗时短（< 30分钟）
- 工具轮次克制（< 50次）
- 工具分布合理（Bash+Edit为主，Execute_code/Agent为辅）
- 无大量重复操作

示例：orbit 26:06/41轮次 → 8分

**中等标准（6-7分）：**
- 耗时适中（30-45分钟）
- 工具轮次适中（50-70次）
- 有一定冗余但目的明确

示例：jetty 44:11/51轮次 → 7分

**低效标准（3-5分）：**
- 耗时过长（> 45分钟）
- 工具轮次过多（> 70次）
- 大量重试、频繁失败、无效操作

示例：nimbus 46:13/70轮次 → 6分

**评分依据的具体写法：**
```
【交付效率】7/10
平台统计数据：耗时 44:11，工具轮次 51 次。
工具分布：TodoWrite 11、Read 0、Write 4、Bash 3、Edit 7、Execute_code 22。
效率分析：Execute_code 使用频繁但目的明确。流程清晰。但 44 分钟偏长，
Read 次数为 0（说明探索阶段主要靠 Execute_code 而非直接读文件）。整体中等偏上。
```

### 阶段五：平台问卷填写

众测平台需要填写三个独立维度（每个 0-10 分）：

| 平台维度 | 对应内容 | 评分方式 |
|---------|---------|---------|
| **模型的综合表现怎么样** | 需求完成度 + 代码质量 + 轨迹质量 | 从本地评分映射 |
| **模型交付效率是否符合预期** | 耗时、工具轮次、工具分布 | 基于平台统计数据 |
| **（必填）模型的产物质量怎么样** | 代码整洁度、产物可用性 | 综合评估 |

**填写顺序严格按照平台表单排列：**

1. 综合表现（0-10）
2. 交付效率（0-10）
3. 产物质量（0-10）
4. 上传截图（>= 5张，每张配说明文字）
5. 写评论（完整评分理由、验收过程、关键发现）

## 致命陷阱一：不验证全栈就打分（最高优先级错误）

**铁律：打分前必须验证完整功能链路。只验证 UI 存在不算验证。**

### 反面教材（我的真实教训）

> 任务 26.1：OpenMAIC 首页集成。我启动了 PHP 服务器，页面正常加载，双 Tab 导航和 AI 课堂入口都存在。
> 点击"AI课堂"显示 loading 动画，我直接判定"AI 课堂功能不可用" -> 需求只给 2/5。
> **实际上这是测试不充分！** iframe 指向 http://localhost:3000，需要 OpenMAIC 服务。
> 我启动该服务后，iframe 成功加载了 OpenMAIC 的完整界面。

**根因：** 只验证了 UI 层（PHP），没有验证底层依赖服务（OpenMAIC）。

### 正确做法

1. **读 TASK_LOG.md**了解模型做了什么——是否安装了依赖、启动了服务
2. **检出产物结构**：有 `node_modules`/`.next` 吗？有 `package.json`/`pnpm-lock.yaml` 吗？
3. **启动所有依赖服务**：
   - 不只要启动主应用的服务器
   - iframe 指向 `localhost:PORT` -> 必须在该端口启动对应的服务
   - 先 `pnpm install`/`npm install`（node_modules 通常被 zip 排除，这是预期行为，不扣分）
   - 如果本地缺少 pnpm: `npm install -g pnpm`
4. **验证完整链路**：主应用 -> 点击功能入口 -> 依赖服务加载
5. **截图取证**：截取完整功能链路的成功状态

### 关于 node_modules 缺失

AI 代码 agent 的交割物通常不包含 `node_modules`（zip 包太大）。但会有：
- `package.json` + lock 文件
- `.next` 构建产物（表示构建已执行）
- `TASK_LOG.md` 中提到已安装依赖

**这不是产品缺陷，不需要加分或减分。** 正常部署时需要额外一步 `pnpm install`。

## 致命陷阱二：一刀切打分

同一任务的不同模型可能差异巨大，必须逐个测试、逐个打分。

### 反面教材

> 任务 26.1 的三个模型（jetty/nimbus/orbit），我给了同样的"封顶 4/10"。
> 实际测试后：jetty AI 课堂正常加载；nimbus CSP 配置有 bug；orbit iframe 渲染有问题。
> 三个模型表现完全不同，一刀切打分完全掩盖了 jetty 的正常工作和 nimbus 的真实 bug。

**根因：** 只分析了 diff 和 TASK_LOG，没有逐个实际运行验证。

### 正确做法

1. 对每个模型单独运行验证
2. 记录每个模型各自的问题（不同模型可能在不同环节出错）
3. 分别打分，不能因为"同任务"就给相近分数
4. 横向对比要具体到技术细节，不能套话

## 致命陷阱三：忽略 CSP/跨域配置（iframe 整合场景特有）

当产物涉及 iframe 嵌入外部服务时，除了验证 HTML/js 是否正确，**必须检查 CSP 头配置**。

详细排障流程参见 `skill_view(name="ai-output-evaluation", file_path="references/iframe-debugging.md")`。

### 真实案例

| 模型 | CSP 配置 | iframe 结果 |
|------|---------|------------|
| jetty | `http://localhost:*` 通配符端口 | 正常加载 |
| orbit | `http://localhost:*` 通配符端口 | 正常加载 |
| nimbus | `http://localhost` 仅端口 80 | 被 CSP 拦截导致空白 |

### 检查要点

1. `.env.local` 中 `ALLOWED_FRAME_ANCESTORS` 是否包含 `:*`（端口通配符）
2. PHP 页面运行在 `localhost:P1`，iframe 加载 `localhost:P2` -> CSP 必须允许 `P1` 或使用 `:*`
3. `Content-Security-Policy: frame-ancestors` 响应头决定谁可以嵌入
- 如果配置了 ALLOWED_FRAME_ANCESTORS，Next.js 自动移除 `X-Frame-Options`，不会冲突

### PHP 运行时错误陷阱

`php -l` 语法检查通过**不代表代码在浏览器中能运行**。常见的仅运行时暴露的错误：

1. **函数重定义**：`Cannot redeclare function get_current_user()` — PHP 不允许定义同名函数两次。如果代码中定义了与 PHP 内置函数同名的函数，或者 `require_once`/`include_once` 路径错误导致多次包含同一文件。
2. **变量作用域**：函数内部访问 `$GLOBALS` 数组不当，或者 `global` 声明遗漏。
3. **文件包含路径**：`require`/`include` 使用相对路径时，当前工作目录与文件所在目录不同。
4. **PHP 版本差异**：8.x 废弃/移除的函数在 8.x 环境中报错。

**验证方式：** 启动 PHP 服务器后用浏览器或 curl 访问页面，而不是只看 `php -l`。

## 致命陷阱四：封顶规则误用

规则：核心需求未完成 -> 总分 <= 6；不可运行/不可验证且无修复指引 -> 总分 <= 4

### 必须做的前置判断

1. 核心功能是否真的不可用？**先试试启动所有依赖服务**
2. 不可用的根因是产品 bug 还是测试环境缺失？
   - **产品 bug**（代码写错、URL 配错、CSP 少端口通配符）-> 封顶生效
   - **测试环境缺失**（没启动服务、没安装依赖）-> 先补齐环境再验证
3. 如果补齐环境后功能正常 -> **不触发封顶**

**正确做法：** 先假设产品可能是好的，全面测试后再下结论。
**错误做法：** 先假设产品可能有问题，没充分测试就扣分。

用户原话："首先，他的课堂都没加载成功，是的吧？课堂没加载成功的前提之下，这个分就不可能及格。"
**但关键前提是：你确实试过让课堂加载成功，而不是想当然认为它不会成功。**

## 自省流程（当董事长指出问题时）

当董事长（用户）指出你的打分有问题时，立即执行以下自省流程，**不要辩解**：

### 第0步：接受批评
直接说"你说得对"，不要解释当时为什么那么做。用户不关心原因，只关心修正。

### 第1步：重读规则
重新打开规则文件（评分提示词），逐条对照自己的打分找违规点。

**常见违规模式：**
- 封顶规则误用（核心需求未完成/不可运行封顶条件判定错误）
- 测试不充分（只测了 UI 层没测依赖服务）
- 截图说明格式/位置错误
- 截图不足（至少 5 张）
- 一刀切评分（所有模型给相近分数）

### 第2步：做缺失的验证
之前没启动的服务现在启动，之前没测的功能现在测。

**典型需要补齐的验证：**
```bash
# 如果依赖 Node/PHP 服务：
cd {产物路径}
pnpm install    # node_modules 缺失是预期行为
pnpm dev        # 启动依赖服务

# 验证完整功能链路
curl http://localhost:PORT/   # 服务是否正常
# 打开浏览器 -> 触发功能 -> 截图记录成功或失败状态
```

### 第3步：逐模型重新测试
不是笼统说"所有模型都有这个问题"。逐个模型运行验证，记录每个模型各自的表现：
- 哪些成功、哪些失败
- 失败的具体原因（CSP bug / 依赖缺失 / 代码错误）
- 截图取证每个状态

### 第4步：重写打分文件
基于验证结果重新打分。修正后向用户汇报：
1. 之前错在哪里（具体违反了哪条规则）
2. 修正后的正确分数和理由
3. 不需要道歉和长篇解释

**成功修正的汇报模板：**
```
我反省了。我的打分有X个问题：

问题一：...
  违反了规则"..."（引用规则原文）
  正确做法：...

修正方案：
- 模型A：N→M分（理由）
- 模型B：N→M分（理由）
```

1. **静默接受，不辩解**。直接说"你说得对"，不要解释当时为什么那么做。
2. **回头重读打分规则**。重新打开规则文件，逐条对照自己的打分。
3. **找出具体违反的规则**。是封顶规则用错了？还是测试不充分？还是截图说明格式不对？
4. **做缺失的验证**。之前没启动的服务现在启动，之前没测的功能现在测。
5. **列出修正方案**。不要只说"我错了"，要说"具体错在哪里 + 修正后的正确做法"。
6. **重写打分文件**。基于验证结果重新打分。

## 常见陷阱

1. **TASK_LOG 位置不固定**：可能在产物根目录、h5web/ 子目录、或模块自己的目录内。根目录没有时搜索：`find {产物路径} -name "TASK_LOG*"`。位置靠内说明模型记录习惯不好，扣分项。
2. **产物文件夹命名不一致**：有些带 `_quick`、`_full` 等后缀，需确认含义。
3. **官方任务书可能为空**：有些期次的官方任务书目录为空，直接用任务清单即可。
4. **端口冲突**：启动本地服务器前检查端口是否被占用。
5. **截图命名必须严格**：`{任务编号}_{模型名}_{中文描述}.png`，不能用错格式。
6. **打分文件是 .txt 不是 .md**：因为最终要粘贴到不支持富文本的网页表单里。
7. **不要一次性铺开所有任务**：以任务为单位，一个一个来。
8. **改错文件（致命）**：有些模型只改了 `studytools/index.php` 而没改 `h5web/index.php`。站点主入口通常是 `h5web/`（如 `edu.7color.vip/` → `h5web/`），`studytools/` 是子路径。改错文件意味着用户从主域名进入看不到任何功能。diff 时注意检查两个入口文件是否都修改了。记录改动行数时两个文件的数值都要记录，差太多说明集成不完整。
9. **独立模块无首页集成（T003/T004 典型模式）**：有些任务（如 AI 小游戏生成器、作文专项）模型只在 `studytools/` 下新建独立模块文件夹，没有修改任何 `index.php`。这意味着：
   - diff 显示 0 行修改（因为没有改动既有文件）
   - 功能只在独立 URL 路径下可用
   - 首页没有入口按钮/导航项
   - 评分时需判断任务是否明确要求首页集成。如果任务说"放在 studytools/下"，那无索引页集成不算缺陷；如果任务说"首页侧边栏出现Tab"，那必须在 index.php 上有改动。
10. **子任务输出格式标准化问题**：派发的子任务可能不按标准格式写打分文件（如用`【综合表现】X/10`代替`总分 X/10：需求 A/5；代码 B/3；轨迹 C/2`）。派发时的 context 要明确指定格式模板，完成后要复查修正。
11. **站点入口与路径差异**：`h5web/` 是主站点根目录（对应 edu.7color.vip/），`studytools/` 是子路径（对应 edu.7color.vip/studytools/）。两个目录下都有独立的 `index.php`，内容相似但路径基准不同。改造时两个文件通常都要改，只改一个意味着另一个入口无变化。
#### 截图数量不足
**铁律：每个模型至少 3-5 张截图，最低目标为每模型 4 张。**
如果某个任务有 4 个模型，总截图目标 = 4×4 = 16 张。以此类推（3个模型→12张，5个模型→20张）。

用户原话：\"按4张算的话，中间只取4张算，那你其实应该是要有，你每个模型，每个文件夹下应该是有4×4，16张截图。\"

**每模型截图覆盖维度：**
1. 主界面（默认状态/布局）
2. 核心功能操作（点击按钮后的关键状态、加载成功/失败结果）
3. 差异/异常（布局差异、错误状态、CSP拦截等）
4. 配置/文件结构（.env.local、TASK_LOG位置、新增模块目录等）

不要在同一个视角上截多张图凑数——每张截图必须有独立的说明价值。

## 截图说明格式必须严格遵循

每张截图在打分文件里配说明，且**放在对应产物（模型）的打分段落内**，不汇总到文件末尾。

格式：

```
文件名.png
  拍的是什么。第一反应。好在哪里/不好在哪里。
```

注意：
- 文件名单独一行
- 说明文字缩进两行（两个空格）
- 必须包含三个要素：拍的是什么、第一反应、好/不好
- 不能只写"截图正常"这种敷衍说明
- **位置很重要：** 在产物段落末尾，紧跟执行效率之后，而不是文件最后
- 每个模型自己的截图说明放在该模型自己的段落里

### 如果有多个产物共享同一张截图

如果多个模型产物的某个功能完全相同（如首页布局），可以用同一张截图，
但需要在每个模型的截图说明中都写上文件名+说明。

## 科研方法论（必须融入整个评测流程）

本任务建议同时加载 `scientific-methodology` 技能（`/skill scientific-methodology`），
该技能定义了董事长-CEO 模式下的执行铁律。

以下铁律在本技能中已内化，但 `scientific-methodology` 技能提供了更通用的执行框架。
**建议每次启动评测前，加载 `scientific-methodology` 技能。**

### 1. 假设先行
改代码/做判断前，先声明假设与依据，验证后再动手。禁止"试着改一下"。
错误示范："先启动 PHP 服务器看看效果" → 正确："假设 iframe 不可用是因为 OpenMAIC 服务未启动，验证方式：启动 OpenMAIC 后刷新页面看 iframe 是否加载。"

### 2. 证据说话
每个论断都要有源码/测试/文档支撑。不确定就说"不确定，需查 X"。
错误示范："AI课堂无法使用" → 正确："AI课堂 iframe 显示空白页面。根因分析：(1) CSP 配置检查：jetty={正确/错误} nimbus={正确/错误} (2) 依赖服务检查：port X 是否可访问 (3) JS 执行检查：dialog 是否正常弹出。"

### 3. 主动质疑
用户方向有问题直接指出，附依据和替代方案。
错误示范："你说得对" → 正确："这个分数可能偏高，因为 iframe 加载失败可能是测试环境问题而非产品 bug，建议先启动 OpenMAIC 再验证。"

### 4. 最小改动
打分文件一行能修就一行。顺手重构是越界。

### 5. 带置信度
确定/大概率(概率%)/不确定，三者必选其一。
例：这个模型不是最佳：大概率(80%)，因为...

### 6. 优先中文表达
在不破坏原意前提下尽可能使用中文表达，少用专有英文词汇。
