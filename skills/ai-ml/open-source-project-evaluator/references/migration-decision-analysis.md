# 迁移/替换决策分析

> 用于评估「已有产品在生产环境运行，是否要迁移到另一个已知产品」的决策场景。
> 区别于从零选型（多个候选选一个开始），核心问题是 **「迁移收益 > 迁移成本 + 迁移风险」**。

---

## 适用场景

- 已有产品 A 在生产环境稳定运行，想评估是否切换到产品 B
- 需要权衡迁移收益 vs 迁移成本 vs 迁移风险
- 决策输出是「保留 / 迁移 / 并行部署」三元推荐

## 分析框架

### Step 1: 建立当前状态基线

记录现有部署的完整状态：

| 维度 | 问题 |
|------|------|
| **部署方式** | Docker / 裸机 / 容器编排？ |
| **数据库** | SQLite / MySQL / PostgreSQL？数据量多大？ |
| **基础设施** | 是否需要 Redis、消息队列等其他组件？ |
| **渠道/配置** | 已配置多少个上游渠道/Provider？ |
| **用户/客户** | 已有多少活跃用户/Tokens/API Keys？ |
| **运维体系** | 是否有自动化 Skill、监控、告警？ |
| **定制化** | 是否有自研修改（代码/配置/模板）？ |

### Step 2: 评估迁移成本

| 成本类型 | 评估维度 |
|---------|---------|
| **数据迁移** | 用户数据、Token 数据、计费记录是否可以无损迁移？格式兼容？ |
| **配置迁移** | 渠道配置、Provider 映射、模型列表的迁移难度 |
| **API 兼容** | 现有客户端是否需要修改？OpenAI 格式是否完全兼容？ |
| **停机窗口** | 是否需要停机迁移？是否可以灰度？ |
| **学习曲线** | 团队对新产品的运维熟练度 |
| **硬件/基础设施** | 是否需要额外组件（如 PostgreSQL、Redis）？ |

### Step 3: 功能差异矩阵

按功能维度逐行对比，标出**「新产品的增量价值」**：

```markdown
| 功能 | 现用(A) | 替代(B) | 增量价值 | 优先级 |
|------|---------|---------|---------|--------|
| 核心能力 | ✅ | ✅ | 持平 | - |
| 特性X | ❌ | ✅ | 描述 | 🔴/🟡/🟢 |
| 特性Y | ⚠️ | ✅ | 描述 | 🔴/🟡/🟢 |
| ... | ... | ... | ... | ... |
```

**增量价值最高 = 🔴**（卡脖子问题），**最低 = 🟢**（锦上添花）。

### Step 4: 风险清单

| 风险 | 等级 | 概率 | 影响 | 缓解措施 |
|------|------|------|------|---------|
| 数据丢失 | 🔴 | 低 | 灾难级 | 完整备份 + 回滚方案 |
| 新产品质量不稳 | 🟡 | 中 | 中 | 测试环境验证 + 灰度 |
| 社区成熟度不足 | 🟡 | 低 | 中 | 核心功能稳定即上线 |
| 合规/ToS 风险 | 🔴 | 中 | 高 | 确认 License + 上游 ToS |

### Step 5: 决策树

```
已有产品稳定运行？
├── 是 → 新产品的增量功能是否是你现在「卡脖子」的问题？
│   ├── 是 🔴 → 评估迁移成本，如果可控则迁移
│   └── 否 🟢 → 不建议迁移，保留现状
├── 新产品有重大合规/ToS 风险？
│   └── 是 🔴 → 不建议迁移
└── 新产品的运维复杂度显著高于现有？
    └── 是 🟡 → 仅在增量价值为 🔴 时考虑
```

### Step 6: 推荐方案

三元输出：

| 推荐 | 条件 | 行动 |
|------|------|------|
| **保留** | 增量价值不是卡脖子问题，或迁移成本/风险过高 | 继续优化现有产品 |
| **迁移** | 增量价值是卡脖子问题，且迁移成本可控 | 规划迁移路线图 |
| **并行部署** | 增量价值有价值但不足以替换现有 | 新业务线用新产品，老业务线保留 |

## 输出格式

推荐用 **Markdown 表格**（非 HTML），结构如下：

1. 现有状态基线
2. 功能对比矩阵
3. 迁移成本评估（数据 / 配置 / API / 运维 / 学习曲线）
4. 风险清单（含缓解措施）
5. 决策树 + 最终推荐

## 参考案例

### 案例：NewAPI → Sub2API 迁移评估

**当前状态：** NewAPI (Docker + MySQL)，13 渠道，Token 服务已上线
**评估结论：** 保留 NewAPI。Sub2API 的增量功能（订阅池化、内置支付）非当前卡脖子问题，且 Sub2API 需要 PostgreSQL+Redis 增加运维复杂度，合规风险更高。

详见该技能的 `references/` 目录下对应的 session-detail 文件（如有）。
