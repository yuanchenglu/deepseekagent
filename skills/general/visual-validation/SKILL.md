# 视觉验收流程

> 视觉验收是对交付质量的最后一道防线。
> 很多问题在代码层没问题，但渲染到 UI 上就不对——只有看才能发现。

---

## 一、什么时候需要视觉验证

| 场景 | 验证对象 | 说明 |
|------|---------|------|
| 阶段 4 高保真原型 | HTML/CSS 原型页面 | 确认视觉方向正确再开发 |
| 阶段 7 最终验收 | 真实运行 APP 截图 | 确认最终效果符合需求 |
| Bug 修复 | 修复前后对比截图 | 确认修复正确 |
| UI 变更 | 变更前后对比 | 防止非预期的 UI 改变 |
| 跨平台验证 | 不同分辨率/设备截图 | 确保响应式效果 |

### ⚠️ 核心原则：真实运行优先

**不要依赖 Playwright 作为唯一验收手段。** Playwright 自动截图只能覆盖预定义的固定状态，不能代替真实的 APP 运行体验。

以下场景必须用**真实运行 APP + 截图 + 识图模型**验证，不能只用 Playwright：
- 交互流程的完整性（点击→跳转→反馈链路）
- 动画/过渡效果
- 空状态/错误状态/边界状态
- 跨页面数据一致性
- 移动端真实渲染效果

**如何执行**：让擅长桌面操控的研发小组（如 CodeX）真实打开 APP、操作、截图，然后用识图模型逐像素看。

## 二、高保真原型审核（阶段 4）

### 审核流程

1. 研发小组出 HTML/CSS 高保真原型
2. 截图或直接浏览器打开查看
3. 用识图模型（MIMO V2.5 / Kimi K2.5）逐页审核
4. 记录问题 → 附截图退回研发小组修改
5. 修改后重新审核，直到通过

### 审核清单

**功能覆盖**（对照需求文档逐条看）：
- [ ] 每个功能点是否有对应 UI 元素？
- [ ] 信息架构是否合理？（用户能不能找到想要的功能）
- [ ] 导航路径是否完整？（用户从 A 到 B 的流程走得通吗）

**像素级**（用识图模型仔细看）：
- [ ] 布局对齐（间距、边距是否一致）
- [ ] 色彩一致性（品牌色、辅助色是否用对）
- [ ] 字体层级（标题/正文/标注的大小粗细是否合理）
- [ ] 图标清晰度
- [ ] 响应式（不同屏幕尺寸是否出问题）

**交互**：
- [ ] 按钮状态（hover/active/disabled）
- [ ] 空状态（没有数据时显示什么）
- [ ] 错误状态（输入错误时怎么提示）
- [ ] 加载状态
- [ ] 动画过渡（如果有）

**审美判断**（主观但重要）：
- [ ] 整体风格是否统一？
- [ ] 视觉层次是否清晰？
- [ ] 有没有明显"丑"的地方？

## 三、最终验收截图（阶段 7）

### 截图规范

每张截图需要：
1. **完整页面**（不是局部，不是裁剪过的）
2. **真实运行状态**（不是设计稿、不是模拟器空白页）
3. **标注关键区域**（用红框/箭头标出需要关注的点）
4. **截图命名**：`{功能模块}_{场景}_{日期}.png`

### 必须截图的场景

- 每个核心功能页面（至少一张）
- 每个交互流程的关键步骤
- 边界状态（空数据、超长文本、错误页）
- 移动端多分辨率（如果适用）

### 反幻觉检查

截图阶段特别注意：
- [ ] 截图是真的运行结果，不是设计稿截图？
- [ ] 截图展示了核心功能，不是只有首页/登录页？
- [ ] 截图包含异常状态，不全是 happy path？
- [ ] 截图不是 AI 生成的占位图？（检查图片真实性）

## 四、识图模型使用方法

### 可用模型

| 模型 | 特点 | 性价比 | 推荐场景 |
|------|------|--------|---------|
| **MIMO V2.5** | 性价比高，识图准确 | ⭐⭐⭐⭐⭐ | 日常验收主力 |
| **Kimi K2.5** | 识图能力也很强 | ⭐⭐⭐⭐ | MIMO 繁忙时备用 |

### 使用方式

在 Hermes 中直接用 `vision_analyze` 工具：

```
vision_analyze(
    image_url="/path/to/screenshot.png", 
    question="检查这个页面的布局是否对齐，颜色是否一致，有没有视觉问题"
)
```

或者用 `browser_vision` 直接看运行中的页面：

```
browser_navigate(url="http://localhost:3000/page")
browser_vision(question="检查这个页面的视觉质量")
```

### 审核时问识图模型的问题

**功能验证类**：
- "这个页面展示了哪些功能？跟需求文档中的 [功能列表] 对比，缺了哪个？"
- "用户完成 [某个操作] 的路径在界面上走不走得通？"

**像素验证类**：
- "这个页面的间距是否一致？标出不一致的地方"
- "颜色有没有偏离品牌规范？"
- "文字的层级（标题/正文/标注）对不对？"

**审美判断类**：
- "这个页面整体视觉质量如何？有什么改进建议？"
- "信息层级是否清晰？用户第一眼看到什么？"

## 五、不同验证方式的选用

| 验证方式 | 优点 | 缺点 | 适用场景 |
|---------|------|------|---------|
| **Playwright 自动截图** | 可重复、标准化 | 只能截固定状态 | 回归测试、CI 流程 |
| **真实运行 APP 截图** | 最真实、覆盖所有状态 | 手动操作、耗时 | 阶段 7 最终验收 |
| **浏览器直接查看** | 实时交互、多角度 | 依赖我手动操作 | 阶段 4 高保真审核 |
| **识图模型分析截图** | 像素级、客观 | 需先有截图 | 所有审核场景 |

**最佳实践**：阶段 4 用浏览器直接查看 + 识图模型分析截图；阶段 7 用真实运行 APP 截图 + 识图模型逐像素验证。

## 六、常见问题清单

| 问题 | 怎么发现 | 怎么修 |
|------|---------|--------|
| 布局错位 | 识图模型看边距 | 退回修改 CSS |
| 颜色偏差 | 对比设计规范颜色值 | 退回修改 CSS 变量 |
| 字体不一致 | 检查 font-family 和 font-size | 退回统一字体 |
| 功能缺失 | 对照需求文档逐个看 | 退回补充 UI |
| 交互不完整 | 检查按钮状态、动画 | 退回补充交互 |
| 响应式断裂 | 多种分辨率截图检查 | 退回修复 CSS |
| 空状态无提示 | 触发空状态检查 | 退回补空状态 UI |
| 截图是伪造的 | 检查图片真实性，看是不是设计稿截图 | 要求小组重新运行截图 |

## 七、本 Skill 的入口判定条件

- 阶段 4（高保真审核）需要视觉验证
- 阶段 7（最终验收）需要截图+识图模型验证
- 任何需要看 UI 质量来判断交付是否合格的场景
