# 产出物文档结构规范 (Deliverable Document Structure)

## 核心原则

**KV Cache 按前缀匹配。文档结构必须遵循：稳定在前，变化在后。**

```
┌──────────────────────────────┐
│ Header + Update Log + 目录    │ ← 最稳定，永远缓存
├──────────────────────────────┤
│ 结论正文（当前正确版本）       │ ← 相对稳定，修正时才变
│ 每个结论标注 [→附录 Q#N]      │   引用指向讨论过程
├──────────────────────────────┤
│ 附录 A：讨论债务               │ ← 引用外部文档
├──────────────────────────────┤
│ 附录 B：Q&A 过程记录          │ ← 不断增长，放最后
│  Q#1, Q#2, ...               │   只影响尾部 Token
└──────────────────────────────┘
```

## 必须包含的元素

### 1. Header
```markdown
# 文档标题 (English Title)

> 创建日期 / 上下文 / 关联文档
```

### 2. Update Log（必须）
```markdown
## 更新记录 (Update Log)

| 时间 | 更新内容 | 来源 |
|------|---------|------|
| YYYY-MM-DD HH:MM | 具体改了什么 | 谁/什么触发的 |
```

### 3. 结论正文
- 只保留当前正确的结论
- 修正痕迹保留（⚠️ 标记 + Update Log 记录）
- 不把讨论过程嵌入正文
- 每个有讨论过程的结论标注 `[→附录 Q#N]`

### 4. Q&A 附录
```markdown
#### Q#N：问题的简短标题
> 时间 | 提问 | 触发

**问题**：原始问题描述

**答案**：结论

> [→ 正文 §X 已体现此结论]
```

## 适用场景

| 文档类型 | 是否适用 |
|---------|---------|
| 架构深度分析 | ✅ 必须 |
| 产品对比分析 | ✅ 必须 |
| 技术方案文档 | ✅ 推荐 |
| **解决方案文档**（如 Code Agent 文档式驱动完整解决方案） | ✅ 推荐 — 解决方案通常经多轮讨论迭代，稳定结论在前、Q&A 在后 |
| **创新点深度文章** | ✅ 推荐 — 每个创新点独立成文，稳定结论(TL;DR+核心方案)在前，验证细节和讨论在后。单篇格式参见 `cross-platform-content-publishing` skill §6 |
| 一次性报告 | ❌ 不需要（不会被反复修正） |
| 纯清单/索引 | ❌ 不需要（没有讨论过程） |

## 更新流程

每次修正时：
1. 修改正文结论
2. 在正文中标注 `[→附录 Q#N]`
3. 在附录 B 追加新的 Q&A 条目
4. 更新 Update Log（记录时间 + 内容 + 来源）
5. 如果 Q&A 是新话题但未深入讨论，先加到附录 A（讨论债务）

## KV Cache 原理说明

```
[Header + 结论正文] ← 这部分几乎不变 → KV Cache 命中 → 近乎免费
[Q&A 附录尾部]     ← 每次追加时只有新增部分未命中 → 成本极小

错误做法：
[Header] [Q&A#1] [结论] [Q&A#2] [结论] ...
→ Q&A#2 插入中间 → 后面所有结论的缓存失效 → 成本爆炸
```
