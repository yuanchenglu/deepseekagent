# KV Cache 优化文档结构 (Document KV Cache Structure)

## 概览

Agent 产出的长文档（> 2KB）随迭代不断膨胀，每次跨 session 读取时全文塞入上下文——Token 消耗线性增长。核心问题不在 Agent 的读取策略，在文档的书写规范。

本 Skill 将 Transformer KV Cache 前缀复用原理应用到文档结构上：把「每次都要读的」核心结论固化在前缀区（YAML 元数据 + TL;DR + 核心论点），把「偶尔才需要的」讨论过程放在尾部变化区。追加新内容时前缀区的 KV Cache 全命中，仅重新计算尾部 Token。

**Token 节省率 > 80%**，不损失信息完整度——改变的只是排列顺序，不是压缩。

## 触发条件

- Agent 正在**创建或修改**一篇超过 **2KB** 的长文档
- 文档预计会被**多次跨 session 读取**
- 文档包含**核心结论 + 讨论过程**两类不同稳定度的内容
- 以下场景**不必触发**：一次性报告、纯清单/索引、短于 2KB 的文档

## 三层结构定义

```
┌──────────────────────────────────────────┐
│ L1 前缀层（稳定层）                        │ ← 创建后不修改，KV Cache ~100% 命中
│  ├ YAML 元数据                            │
│  ├ TL;DR（≤ 300 字）                      │
│  └ 核心结论列表（3-5 条，每条 ≤ 50 字）   │   典型大小占比 ~5%
├══════════════════════════════════════════┤
│ L2 正文层（半稳定层）                      │ ← 偶尔修改/补充，KV Cache ~90% 命中
│  ├ 详细分析 / 论证过程                    │   典型大小占比 ~45%
│  └ 数据支撑 / 案例分析                    │
├══════════════════════════════════════════┤
│ L3 变化层（动态层）                        │ ← 只追加不插入，不影响前缀缓存
│  ├ 讨论记录 / Q&A                         │   典型大小占比 ~50%
│  └ 迭代笔记 / 附录                        │
└──────────────────────────────────────────┘
```

### L1 前缀层（稳定层）

**写入规则：创建后不修改。如核心结论确实变更，应重构全文档而非局部修改。**

必须包含以下三个元素：

#### 1) YAML 元数据

```yaml
---
title: <文档标题>
created: <创建日期 YYYY-MM-DD>
innovation_points: [<关联创新点 ID 列表>]
kv_cache_stable: true
---
```

`kv_cache_stable: true` 是给 Agent 的信号：「前缀区已按 KV Cache 优化结构排列，核心结论在读前 500 tokens 内。」

#### 2) TL;DR 结论

紧跟在 YAML 元数据后，不超过 **300 字**。用 blockquote 格式：

```markdown
> **TL;DR** — 文档最核心的结论，一段话讲清楚核心观点和价值。
```

#### 3) 核心结论列表

TL;DR 之后，3-5 条结论，每条不超过 **50 字**：

```markdown
## 核心结论
1. <结论一，简明扼要>
2. <结论二，简明扼要>
3. <结论三，简明扼要>
```

### L2 正文层（半稳定层）

- 详细分析、论证过程、数据支撑、案例分析
- 可偶尔修改（补充证据、修正错误）
- 修改不改变 L1 前缀层的内容
- 每个有讨论过程的结论标注 `[→附录 Q#N]`

### L3 变化层（动态层）

- 讨论记录、Q&A 附录、迭代笔记
- **只追加不插入**——所有新内容追加到文件末尾
- 追加新内容不改变 L1/L2 的任何内容
- 每次追加在 Update Log 中记录（时间 + 内容 + 来源）

## 检查清单

Agent 应用此 Skill 创建或修改文档后，必须逐项检查：

1. [ ] 前缀 YAML 是否包含 `kv_cache_stable: true` 标记？
2. [ ] TL;DR 是否在文档前 500 tokens 内且不超过 300 字？
3. [ ] 核心结论列表是否完整（3-5 条，每条 ≤ 50 字）？
4. [ ] L1 前缀层是否创建后未修改过？（新文档跳过此项）
5. [ ] 新增内容是否只追加到文件末尾（未插入 L1/L2 中间）？
6. [ ] 文档是否 > 2KB？（< 2KB 的短文档不需要此结构）

## 正确 vs 错误示例

### ✅ 正确结构（KV Cache 优化）

```markdown
---
title: Plan 架构深度分析
created: 2026-05-25
innovation_points: [I-01, I-03, I-04]
kv_cache_stable: true
---

# Plan 架构深度分析

> **TL;DR** — Plan 是发散性问题，Reason 是收敛性问题。
> First Principles 拆解是连接两者的桥梁。

## 核心结论
1. OMO 的 Plan 是扁平 checklist，无依赖图
2. 级联修正引擎必须基于有向依赖图
3. 审查严格度应 = f(KV Cache 占用, Plan 复杂度)

---

## 详细分析
[完整保留的正文内容]

## 讨论附录
### Q#1：[新讨论追加在末尾]
### Q#2：[再新讨论追加在末尾]
```

### ❌ 错误结构（非优化）

```markdown
# Plan 架构深度分析

## 1. 引言
[500 字背景铺垫]

## 2. Plan vs Reason
[核心结论被埋在第二节，Agent 需要读 ~2KB 才能到达]

## 3. 讨论记录
[讨论和正文混排]
```

**错误分析：**
1. 缺少 YAML 元数据和 `kv_cache_stable` 标记——Agent 不认识
2. 无 TL;DR——Agent 读完 2KB 还不知道核心结论
3. 核心结论被埋在正文中段——每次读取都要编码全文
4. 讨论和正文混排——追加讨论导致后续所有内容的 KV Cache 失效

## 常见误区

1. **讨论记录写在正文中间**——追加讨论时导致后续所有内容的 KV Cache 失效。讨论必须放在 L3 变化区。
2. **TL;DR 太长（> 300 字）**——失去了「快速获取核心结论」的意义，Agent 仍需翻页。
3. **核心结论超过 5 条**——超过 5 条说明没提炼到本质。重新归类或分层。
4. **修改 L1 前缀层**——L1 修改导致 KV Cache 全量失效，收益归零。如果核心结论真变了，重构全文档而非局部修改。
5. **对所有文档都硬套此结构**——< 2KB 的短文档、一次性报告不需要。软指引，不强求。
6. **忘记更新 L3 的追加记录**——每次追加应在尾部注明时间和来源，便于追踪文档演变。
