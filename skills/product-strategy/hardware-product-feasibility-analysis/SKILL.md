# 硬件产品技术可行性分析

从 CTO 视角，对硬件产品想法做第一性原理分析。不写商业计划书，只回答一个问题：**"这东西技术上能不能做，难点在哪，第一步该验证什么。"**

## 触发条件

- 用户提出一个硬件产品想法（特别是 IoT/消费电子/嵌入式类）
- 用户询问某个传感/检测方案是否可行
- 用户需要一个技术验证路线图

## 分析框架（七步法）

### 第一步：拆解被测对象的物理/电气原理

先搞清楚"被检测的东西"是什么物理量、有多大、在什么条件下产生。

```
关键问题：
- 被测物理量是什么？（电流/电压/声音/光/振动/...）
- 信号幅度多大？（mV级？V级？μA级？）
- 信号持续时间？（μs？ms？s？）
- 背景噪声水平？（什么会干扰这个信号？）
- 有没有可参考的类似检测方案？
```

### 第二步：列出至少 2-3 种检测方案并做对比矩阵

永远不要只给一种方案。强制给出至少两种，对比维度包括：

| 维度 | 权重 | 说明 |
|------|------|------|
| 实现难度 | 高 | 电路复杂度、元器件可得性 |
| 成本（量产） | 高 | 单台 BOM 增量成本 |
| 安全性 | 高 | 高压隔离、安规认证 |
| 信号区分度 | 最高 | 能否区分目标信号和干扰 |
| 量产一致性 | 中 | 是否需要逐台校准 |
| 成熟度 | 中 | 有没有人做过类似的东西 |

### 第三步：深度分析假触发/误判场景（这一步决定产品生死）

这是最重要的部分。列一个表：

| 假触发场景 | 信号特征 | 与真信号的差异 | 判别策略 |
|-----------|---------|---------------|---------|
| 场景 A | ... | ... | ... |
| 场景 B | ... | ... | ... |

每个假触发场景都要给出具体的判别策略（阈值、时间窗口、多模验证等）。

### 第四步：BOM 成本估算

按量产 10K+ 规模估算核心元器件成本：

```
| 元器件 | 型号 | 单价 | 说明 |
| MCU | ESP32-C3 | ¥8-12 | BLE 5.0, RISC-V |
| 传感器 | ... | ... | ... |
| ... | ... | ... | ... |
| 合计 | | ¥XX-XX | |
```

### 第五步：风险评估（含反方观点）

必须给出"为什么这个产品可能失败"的分析：

- **技术风险**：核心假设不成立、信号区分度不够
- **量产风险**：一致性、校准、供应链
- **安全风险**：高压、安规、认证
- **竞争风险**：大厂跟进、专利障碍
- **市场风险**：需求真实性、季节性

每项风险给出"破法"建议。

### 第六步：参考实现分析

搜索并分析已有的开源项目/论文/竞品：

```
1. 搜索关键词组合（GitHub、Hackster.io、Instructables、专利数据库）
2. Clone 关键项目，读源码（遵循 source-code-verification 原则）
3. 提取：
   - 他们用了什么方案？
   - 哪些参数是实测调出来的？（去重窗口、阈值等——直接继承）
   - 他们踩了什么坑？（EMI 干扰、校准问题——提前规避）
   - 他们没做什么？（我们的差异化空间）
4. 写对比分析文档，标注源码位置
```

**关键原则**：参考项目的"经验参数"（如去重窗口 700ms）可以直接继承，因为它们是用真实数据调出来的，不是拍脑袋的。

### 第七步：分阶段验证计划

**Phase 1 — 核心假设验证（2-3 周，最低成本）**
- 目标：验证"信号能不能被可靠检测和区分"
- 方法：买现成硬件 + 示波器/ADC 抓数据
- 需要的东西：具体采购清单（型号、价格、数量）
- 成功标准：量化的区分度指标（如"真击杀 vs 金属短路可区分度 ≥ 90%"）
- **这是整个项目的 Go/No-Go 决策点**

**Phase 2 — MVP 原型（4-6 周）**
- 目标：开发板搭建可工作的原型
- 输出：能跑的代码 + 基础算法

**Phase 3 — 产品化（8-12 周）**
- 目标：定制 PCB、外壳、App、认证

## 输出规范

### 必须包含的元素

1. **一句话结论**（开头）：技术上可行/不可行，核心难点在哪
2. **原理拆解**：带框图的电路/系统说明
3. **方案对比矩阵**：至少 2 种方案
4. **假触发/误判分析表**：至少 4 种场景
5. **BOM 成本表**：核心器件选型和价格
6. **风险矩阵**：含反方观点和破法
7. **Phase 1 验证计划**：具体到采购清单和测试矩阵
8. **参考实现分析**：如果有人做过，必须分析

### 文档风格

- 用表格做对比，用 ASCII 框图做架构
- 关键参数标注来源（"源码 L403"、"实测数据"、"推算"）
- 推断 vs 确认要区分（"待 Phase 1 验证" vs "已验证"）
- 评分用星级（⭐⭐⭐⭐⭐）

## 常见陷阱

1. **跳过假触发分析** — 这是最致命的问题。传感器能检测到信号 ≠ 能可靠区分真假。假触发分析是产品能不能用的关键。
2. **只给一种方案** — 剥夺了决策者的选择权。至少要有主方案 + 备选方案。
3. **不给出反方观点** — 只讲好处不讲风险，等于帮用户自我欺骗。
4. **跳过 Phase 1 直接谈量产** — 核心假设没验证，后面的都是空中楼阁。
5. **忽略参考实现** — 如果 2021 年就有 Arduino 爱好者做过类似的东西，他的经验参数就是免费的技术顾问。

## 项目文档结构

当分析后需要创建项目时，使用以下结构（适用于硬件+软件产品）：

```
project/
├── README.md                      # 项目总览
├── docs/
│   ├── 01_产品/                   # 产品定义、游戏化设计、需求文档
│   ├── 02_技术/                   # 技术可行性、硬件架构、参考实现分析
│   ├── 03_设计/                   # UI/UX、品牌 VI、工业设计
│   └── 04_运营/                   # 增长策略、内容运营、活动策划
├── hardware/
│   ├── schematics/                # 电路原理图
│   ├── firmware/                  # MCU 固件代码
│   └── enclosure/                 # 外壳结构设计
├── app/                           # 移动端/Web App 代码
└── assets/                        # 图片、音效、字体等资源
```

## 产品化扩展（阶段 2-5）

以下内容从 `hardware-product-blueprint` 技能整合而来，覆盖技术可行性验证之后的产品化流程。

### 阶段 2：产品定义

#### 2.1 一句话 + 定位
- 不是\"更好的 XX\"，是\"不一样的 XX\"

#### 2.2 目标用户画像
| 画像 | 特征 | 场景 | 动机 |
早期不要试图服务所有人，标注种子用户是谁。

#### 2.3 产品形态
- 硬件：定价、核心功能、脱离 App 能否独立使用
- App：核心模块、DAU 目标
- 数据层：什么数据有价值、谁能用、怎么变现

#### 2.4 北极星指标
一个数字定义产品健康度。不是\"硬件出货量\"。

### 阶段 3：游戏化系统设计（按需）

#### 3.1 核心循环：动作 → 即时反馈 → 看变化 → 分享 → 继续

#### 3.2 六层设计框架
1. **等级体系**：前期快（正反馈密集，推荐前 5 级 2 小时内达成），后期慢（稀缺感）
2. **成就系统**：70% 可预期 + 20% 挑战 + 10% 隐藏惊喜
3. **战队系统**：这是留存核心——\"我虽然菜，但我战队强\"
4. **领地争夺**：LBS 网格 + 战队积分，产生天然 UGC 故事线
5. **赛季与活动**：全年日历 + 节日限定
6. **经济系统**：多货币 + 消耗品 + 获取渠道闭环

详细设计参考 `references/gamification-design-cheatsheet.md`

**核心理念**：排行榜只对前 10% 用户有意义。战队系统（群体归属）+ 领地争夺（空间叙事）+ 隐藏成就（惊喜制造）才是让 100% 用户有参与感的设计。

### 阶段 4：壁垒分析

| 层 | 壁垒强度 | 说明 |
|----|----------|------|
| 硬件 | ★☆☆☆☆ | 分分钟抄走 |
| App 功能 | ★★☆☆☆ | 可抄，但社交关系链搬不走 |
| 数据 | ★★★★☆ | 时间积累，后来者从零开始 |
| 品牌即品类 | ★★★★★ | 终极壁垒 |

```
│   ├── 03_设计/                   # UI/UX、品牌 VI、工业设计
│   └── 04_运营/                   # 增长策略、内容运营、活动策划
├── hardware/
│   ├── schematics/                # 电路原理图
│   ├── firmware/                  # MCU 固件代码
│   └── enclosure/                 # 外壳结构设计
├── app/                           # 移动端/Web App 代码
└── assets/                        # 图片、音效、字体等资源
```

### 核心原则（产品化）

1. **先回答\"能不能做\"，再谈\"怎么做\"** — Phase 1 验证通过前不谈产品化
2. **误判问题比检测问题更难** — 分不清真信号和假信号是产品失败的第一原因
3. **竞争壁垒不由硬件决定** — 消费硬件门槛低，量产后 3 个月被抄。想清楚火了之后抄不走的是什么
4. **游戏化不是加个排行榜** — 排行榜只对前 10% 有用
5. **文档结构 = 01_产品 / 02_技术 / 03_设计 / 04_运营** — 四大类覆盖创意到落地完整链路
