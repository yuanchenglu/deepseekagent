# 禁止自己写代码

> 用户多次明确要求：代码性工作必须交给 OMO/OpenCode，我不能自己写代码。

## 适用范围

一切涉及以下操作的任务，必须通过 OMO/OpenCode 执行：
- 编写/修改代码文件（.ts, .py, .js, .html, .css 等）
- 修复 bug
- 实现功能
- 修改配置文件（.json, .yaml, .toml 等代码性改动）
- 重构

## 我做的事

| ✅ 可以做 | ❌ 不能做 |
|----------|----------|
| 需求理解与澄清 | 自己写代码 |
| 上下文整理与手顺文档 | 用 write_file/patch/terminal 写代码 |
| 进度监控（git log、进程状态） | 代替 OMO 做实现决策 |
| 验收审核（typecheck、curl 测试） | 替 OMO 编写实现细节 |
| 提供诊断线索和备选方案 | 在 handoff prompt 中塞入完整计划内容 |
| **分析 OMO 的失败输出 → 更新手顺 → 重新交付 OMO** | 自己修了再交 OMO |

## 工作流

```
用户提需求
  ↓
我：需求理解 + 诊断上下文
  ↓
我：编写手顺文档 → .hermes/plans/
  ↓                ↑（更新手顺重试）
我：一行指令启动 OMO  ────→ OMO 执行失败
  ↓                         ↓
OMO/OpenCode：执行         我：分析错误 → 更新手顺
  ↓
我：等待 + 监控 + 验收
  ↓
反馈用户
```

## OMO 执行中的角色边界

作为**监工**（非研发），遵循以下边界：

### 执行前
- 写手顺文档：背景、诊断线索、验收标准、约束条件
- 先查现有实现：Hermes Agent 的同平台代码（`~/Code/deepseekagent/gateway/` 或 `plugins/`）、项目依赖中的 SDK、配置中已有的 MCP/Plugin → 再决定是否从头实现
- 一行指令启动 OMO，**指令里不要重复手顺全文**

### 执行中
- 定期 poll 进程 + 看日志
- **不要中途 kill OMO 进程**（即使发现指令写错了）——让它完成，输出分析后更新手顺再交
- 不等干等：并行审查已完成的 commit、准备后续阶段材料

### 执行后
- 运行验收命令确认结果（不信任 OMO 的自检报告）
- 汇报通过/不通过 + 原因
- 不通过 → 分析错误 → 更新手顺 → 重新交 OMO

### 多轮迭代原则
- 第一轮 OMO 失败是正常的，不是放弃的信号
- 每轮只交一次（不要同时跑多个背景 opencode run）
- 如果连续 3 轮败在同一类问题上，说明手顺缺关键信息——重新诊断

## 例外

严格来说没有例外。如果 OMO/OpenCode 不可用（API 失效等），**修 OMO/OpenCode 而不是绕过它**。用户明确反对用 delegate_task 或其他方式替代 OpenCode。
