# KV Cache 优化文档结构 (KV-Cache Optimized Document Structure)

> 来源: 与袁老师的 Plan 架构深度讨论中演化出的文档组织模式
> 记录时间: 2026-05-25

## 核心原则

**KV Cache 按前缀匹配。稳定放前面，变化的放后面。**

```
文档结构（KV Cache 优化版）:

  ┌──────────────────────────────┐
  │ 标题 + 元数据 + Update Log    │ ← 最稳定，永远缓存命中
  ├──────────────────────────────┤
  │ 关联文档引用                  │ ← 稳定
  ├──────────────────────────────┤
  │ 结论/分析正文                 │ ← 相对稳定，修正时才变
  │ （过程文档的链接在这里引用）    │
  ├──────────────────────────────┤
  │ Q&A 附录（过程记录）          │ ← 不断增长，放最后
  │  · Q#1: 问题 + 答案          │   追加时只影响尾部Token
  │  · Q#2: 问题 + 答案          │   Header + 结论缓存全命中
  │  · ...                        │
  └──────────────────────────────┘
```

## 为什么不用两个文档

- 过程是结论的证据链 → 放在一起才有可追溯性
- Q&A 追加时只影响文档尾部 → Header + 结论部分的 KV Cache 不受影响
- AI 读取时优先读 Header+结论，需要时再翻附录 → 不用每次全量读

## 正文引用约定

正文中如果某个结论来自某次 Q&A 讨论，用 `[→附录 Q#N]` 标注来源。这样：
- 读者看正文就够了
- 想追溯"为什么是这个结论"时翻附录
- 正文保持稳定、不嵌入长讨论

## 实际案例

`Plan架构深度分析-Plan-Architecture-Deep-Analysis.md` 是第一个采用此结构的文档：
- Header + Update Log: ~35 行
- 结论正文 §1-7: ~570 行（9 个 Q&A 嵌入交叉引用）
- 附录 B Q&A 过程记录: ~105 行（9 条 Q&A）

## Update Log 规范

每个文档头部应有 Update Log 表格：

```markdown
## 📋 更新记录 (Update Log)

| 时间 | 更新内容 | 来源 |
|------|---------|------|
| 2026-05-25 16:30 | 文档结构重组 | 袁老师指导 |
| 2026-05-25 10:00 | 初始版本 | 苏格拉底对话综合 |
```

时间精确到分钟，来源标注清楚（提问/指正/源码验证/对话综合）。
