# LLM 物理特性兼容性分析

当用户问"某个 Agent 平台能否发挥特定 LLM 的物理特性"时（如"Ruflo 能否利用 DeepSeek 的 MLA/MoE/1M Context"），使用这套方法论。

## 与"模型特定优化分析"的区别

| 维度 | 已有: 模型特定优化分析 | 本: 物理特性兼容性分析 |
|------|----------------------|---------------------|
| **问题方向** | 平台 → 模型：平台为模型优化了什么？ | 模型 → 平台：平台架构能否发挥模型特性？ |
| **起点** | 平台的代码（找缓存策略、token 压缩、工具路由） | 模型的物理特性（MoE、MLA、KV Cache、推理能力、成本结构） |
| **终点** | 优化清单（具体实现 + 行号） | 兼容性结论（能用/需改/需重做）+ 阻力的根因 |
| **参考文件** | `llm-agent-optimization-checklist.md` | 本文 |

典型触发场景：
- "分析 X 框架能否利用模型 Y 的 1M 上下文"
- "X 平台是否发挥了模型的 KV Cache 优势"
- "这个编排平台能不能感知模型的 MoE 稀疏激活"
- "clone 到本地分析，看它能否应用 DeepSeek 的物理特性"

## 六步分析法

### 第一步：架构分层映射（必须基于源码）

将目标平台按以下层次拆解，标注每个层的实现文件和关键接口：

| 层次 | 分析要素 | 核心问题 |
|------|---------|---------|
| **1. Provider/通信层** | API 格式、支持的模型列表、专有参数 | 模型是否有专属 provider？还是走通用接口？ |
| **2. 模型路由层** | 选模型策略、tier 体系、成本模型 | 路由是否硬编码了某个模型的 tier 体系？ |
| **3. 自学习/Intelligence 层** | SONA、MoE、RL 路由、pattern 学习 | 学的是 agent 类型还是模型偏好？ |
| **4. Agent 执行层** | Swarm、任务分配、agent 间通信 | 模型特性是否影响 agent 间协作模式？ |
| **5. 记忆/上下文层** | Context Window、压缩策略、KV Cache 管理 | 长 context 是否被合理利用或压缩？ |
| **6. UI/接入层** | 模型选择界面、路由配置 | 是否已有目标模型的路由配置？ |

**源码验证原则**：每一层必须通过 search_files + read_file 定位到具体实现文件，不能从 README 推断。

### 第二步：模型物理特性枚举

列出目标模型**实际不同于通用模型的物理特性**，不列功能（如"支持 tool calling"不算物理特性）。

DeepSeek 案例：

| 特性 | 本质 | 对平台意味着什么 |
|------|------|----------------|
| **MoE 稀疏激活** | 671B 总参数但每 token 只激活 37B，推理时 CUDA memory 远低于同规模 dense 模型 | 资源估算、并发策略可以更大胆 |
| **MLA (Multi-head Latent Attention)** | KV Cache 压缩到 ~1/4 标准 MHA，同 context 长度下缓存占用小 | 长上下文场景的缓存压力远低于 Claude/GPT |
| **中大 Context Window** | V4 支持 1M token | 路由策略需要区分"短"和"超长"上下文 |
| **reasoning_effort 控制** | 可控制推理深度（low/medium/high） | 路由层需要感知此参数，按任务复杂度动态设置 |
| **成本结构差异** | V4 Flash 极便宜，V4 Pro 约 4.2x | 不同 tier 的差价远小于 Claude 的 25x，bandit 奖励函数需要重新设计 |
| **CoT 思维链输出** | R1 输出 `...` 推理过程 + 最终答案 | Provider 层需要后处理分离推理链和答案，可增强自学习信号 |

### 第三步：逐层逐特性对照

建立矩阵。行 = 模型特性，列 = 平台层次。

对每个格子回答三个问题：
1. **意识**：平台这层知道这个特性存在吗？（源码搜索关键词）
2. **接口**：平台这层有参数/接口/模型来表达这个特性吗？
3. **利用**：平台这层能从这个特性中获益吗？如何获益？

### 第四步：三档分类

| 分类 | 含义 | 例子 |
|------|------|------|
| ✅ 直接能用 | 通用接口天然兼容，无需改代码 | 通过 OpenAI 兼容接口调 DeepSeek API |
| 🔧 需要改造 | 加字段/参数/配置即可 | 加 `reasoning_effort` 参数、更新 maxContextLength |
| 🔴 需要重新设计 | 平台架构假设与模型特性冲突 | Claude 3-tier 路由体系 vs DeepSeek 扁平差价 |

### 第五步：抽象层不匹配分析（最重要的一步）

很多"不能利用"的根因是**抽象层不同**，而非代码缺陷。需要追问：

模型物理特性的抽象层 vs 平台架构的抽象层：

```
例: Ruflo 的 MoE router 是 Agent 选择层（coder/tester/architect）
   DeepSeek 的 MoE 是推理参数层（37B active per token）
   两者在不同层——不冲突，但也不能互相利用

例: Ruflo 的成本模型（bandit reward function）在 路由决策层
   DeepSeek MLA 的节约在 推理执行层
   路由层按"是否成功"反馈，不按"用了多少 KV Cache"反馈
```

追问框架：
- **这个特性在哪个抽象层产生影响？**（推理层、通信层、调度层、还是经济层？）
- **平台的对应层能感知这个影响吗？**（有没有指标/计数器？）
- **如果现在不能，加一层适配的代价有多大？**（改一个文件 vs 改整个路由架构）

### 第六步：输出结构

最终结论输出为三层矩阵：

```
## 能直接用的
| 特性 | 说明 |
|------|------|
| 调 API | ✅ 通过 OpenAI 兼容接口，改 apiUrl 即可 |

## 需要改造才能用的
| 特性 | 改造难度 | 改造内容 |
|------|---------|---------|
| reasoning_effort | 低 | LLMRequest 加字段，Provider 透传 |

## 架构上需要重新设计的
| 特性 | 改造难度 | 问题本质 |
|------|---------|---------|
| 成本感知路由 | 高 | Claude 的 tier 体系与模型实际差价不匹配 |
```

附上"本质追问"段落，回答"为什么不能"的根本原因。

## 实战案例

### Ruflo × DeepSeek（2026-06-12 分析）

完整分析报告：`~/Code/ruflo/deepseek-analysis.md`

**关键发现**：
- Provider 层：无 DeepSeek 专属 Provider，走 OpenAI 兼容接口
- 路由层：Claude 3-tier 硬编码（`ClaudeModel = 'haiku'|'sonnet'|'opus'`），无 reasoning_effort 参数
- Intelligence 层：model-agnostic，不影响
- Agent 执行层：model-agnostic，不影响
- 记忆层：maxContextLength 上限 128K，不支持 1M
- UI 层：已有 DeepSeek 静态路由（ruvocal routes.chat.json），但不智能

**抽象层不匹配核心发现**：
1. MLA 节存在推理执行层，平台调度层不需要感知
2. MoE 稀疏激活在模型推理层，平台的 Agent MoE 在编排层——同名不同物
3. 路由层的成本 bandit 奖励函数与模型实际差价完全不匹配（Claude 25x gap vs DeepSeek 4.2x gap）
